# CI-004 — Gouverner les trains feature et release versionnés

- **Statut :** Prêt pour revue — fusion humaine requise
- **Date d'ouverture :** 2026-09-05
- **Responsable de décision :** Porteur du Betting Project
- **Exécutant :** Codex
- **ADR applicables :** ADR-005, ADR-008
- **Train de version :** bootstrap antérieur au premier train
- **Branche d'intégration :** aucune créée par ce lot
- **SHA de départ :** `3fb224e9724698324a56b47fe5d943ecd366f197`, HEAD exact de `main`
- **Branche de travail :** `codex/ci-004-version-branch-workflow`
- **Cible de Pull Request :** `main`, exception de bootstrap unique et bornée au SHA ci-dessus

## Objectif

Remplacer l'ancien flux à branche permanente unique par un contrat exécutable de trains versionnés,
sans créer prématurément les nouvelles références : Work Orders et Pull Requests sont gérés sur
GitHub autour d'une branche feature d'intégration ; seule la promotion feature vers release passe
par une Merge Request GitLab fast-forward.

## Décisions matérialisées

- un train de branche vaut exactement `Vx.y.z`, `Vx.y.z-RCnn` ou
  `Vx.y.z-RCnn-SNAPSHOT`, avec un cœur SemVer sans zéro initial et `nn` exactement de `01` à `99` ;
- `feature/<TRAIN>` est la branche d'intégration canonique GitHub puis synchronisée vers GitLab ;
- `release/<TRAIN>` est propre à GitLab et relève du seul motif de branche protégé `release/V*` ;
  les tags GitLab `v*` sont protégés séparément sans constituer des branches protégées ;
- une branche de Work Order vaut exactement
  `feature/<TRAIN>-(CODEX|HUMAN)-<WORK-ORDER>`, part du HEAD documenté de sa feature cible et se
  clôt par une Pull Request vers cette même feature ; `<WORK-ORDER>` suit `<TYPE>-<NNN>` avec
  `NNN=001..999` et possède son document sous `docs/work-orders/` ;
- la Pull Request finale `feature/<TRAIN>` vers `main` produit un merge commit `M`, puis la feature
  porte déjà la version Maven exacte et avance normalement en fast-forward vers `M` avant
  synchronisation ;
- la Merge Request GitLab `feature/<TRAIN>` vers `release/<TRAIN>` exige le même train, une cible
  protégée, le même projet, une version Maven conforme et un graphe où le SHA de pipeline, la
  feature distante et `main` désignent `M`, avec la release cible ancêtre de `M` ;
- les branches utilisent `RC01` à `RC99`, tandis que Maven et les tags conservent `rc.1` à `rc.99`.
  Un tag `rc.100` reste conforme à la grammaire SemVer historique mais son packaging est refusé,
  faute de train de branche représentable ;
- les snapshots durables proviennent uniquement d'un pipeline `push` de la branche feature
  d'intégration exacte. Les bundles de Work Order, Pull Request et `main` restent éphémères ;
- tout pipeline de branche GitLab, quelle que soit sa source, accepte seulement `main`, une feature
  d'intégration exacte ou une release exacte ; les branches de Work Order, le bootstrap et les
  références historiques y sont refusés. Les Merge Requests et tags suivent leurs voies dédiées,
  et une source sans branche, tag ni contexte de Merge Request échoue ;
- tout pipeline de tag GitLab échoue dès `validate:source` si le tag n'est pas protégé ou ne suit
  pas exactement `vX.Y.Z` ou `vX.Y.Z-rc.N`, même lorsqu'aucun job de packaging ne serait sélectionné ;
- les contextes GitLab sont mutuellement exclusifs : une Merge Request porte des branches source et
  cible non vides mais aucun `CI_COMMIT_BRANCH`/`CI_COMMIT_TAG` ; une pipeline de branche ou de tag
  refuse toute variable de Merge Request résiduelle ;
- le dépôt conserve `production.approved=false` et `vps.deployable=false` jusqu'à OPS-001.

## Périmètre autorisé

- aligner AGENTS.md, ADR-005, ADR-008, le runbook et le modèle de Work Order ;
- versionner un modèle de Pull Request GitHub et le contrat de registre commun ;
- renforcer les gardes de nommage, de topologie GitHub, de Merge Request GitLab et de packaging ;
- limiter la conservation des snapshots aux branches feature d'intégration exactes ;
- ajouter les tests positifs et négatifs des formes stables, RC et RC-SNAPSHOT ainsi que du
  bootstrap historique borné, avec des graphes Git réels.

## Exclusions

- aucune création des trains distants `feature/V*` ou `release/V*`, aucune suppression, protection,
  synchronisation ou promotion de ces trains ; seule la publication de la branche de bootstrap et
  de sa Pull Request vers `main` relève de ce lot ;
- aucun renommage ou effacement des branches historiques `codex/*`, `human/*` ou `hotfix/*` ;
- aucune fusion, création de tag ou publication d'artefact ;
- aucune activation de production ou modification de la frontière OPS-001 ;
- aucune modification applicative, dépendance ou migration.

## Critères d'acceptation

- [x] Les trois formes de train et les seules formes RC `RC01` à `RC99` sont cohérentes dans les
  documents, scripts et tests.
- [x] Les gardes distinguent une feature d'intégration exacte d'une branche de Work Order.
- [x] Le garde GitHub accepte seulement Work Order vers feature de même train, feature vers `main`
  et l'exception CI-004 exactement bornée ; il contrôle la version Maven, le SHA de tête et le
  merge-base historique. Le bootstrap exige en plus `0.1.0-SNAPSHOT`.
- [x] Le garde GitLab préserve ses contrôles de projet, protection et scellement, puis accepte
  seulement feature vers release de même train avec mapping Maven déterministe, égalité des SHA
  source/main/pipeline et ascendance de la release cible sur un historique complet.
- [x] Un tag de release exige le SHA exact de `main`, de la feature canonique et, sur GitLab, de la
  release canonique ; `rc.100` échoue explicitement.
- [x] Le job `validate:source` refuse tout tag GitLab non protégé ou hors grammaire SemVer avant les
  règles conditionnelles du job de packaging.
- [x] Le routeur GitLab refuse tout mélange MR/branche, MR/tag, branche/variables MR ou tag/variables
  MR, ainsi qu'une Merge Request sans source ou cible.
- [x] Aucun snapshot durable n'est téléversé depuis `main`, une branche de Work Order ou une Pull
  Request ; le packaging vérifie néanmoins le train Maven de la branche Work Order réelle.
- [x] Un pipeline de branche GitLab refuse les branches de Work Order, le bootstrap et les
  références historiques, tout en acceptant `main`, les features d'intégration et les releases
  exactes pour les sources push, web, schedule, API, trigger et pipeline.
- [ ] Toutes les commandes de test ci-dessous sont vertes sur le diff final.
- [ ] La Pull Request de bootstrap reçoit les checks Windows/Linux verts, les discussions résolues
  et une revue humaine avant merge commit.

## Commandes de test

```text
sh ci/test-branch-name.sh
sh ci/test-github-pull-request.sh
sh ci/test-gitlab-merge-request.sh
sh ci/test-gitlab-workflow.sh
sh ci/test-release-reproducibility.sh
sh ci/test-package-guards.sh
sh scripts/tests/check-no-secrets.Tests.sh
./scripts/check-no-secrets.sh --scope all --base origin/main
git diff --check origin/main...HEAD
```

Les contrôles Maven complets ne sont pas requis pour la réalisation locale de ce lot exclusivement
documentaire et shell ; les workflows distants exécuteront néanmoins les suites Windows, Maven et
PostgreSQL habituelles sur le commit publié.

## État distant constaté avant réalisation

Au 2026-09-05, aucune nouvelle référence `feature/V*` ou `release/V*` n'est déclarée comme créée par
ce Work Order. Les dépôts GitHub sont configurés avec merge commit autorisé, squash et rebase
désactivés, et suppression automatique de la branche source désactivée. Les projets GitLab sont
configurés en fast-forward, squash interdit, pipeline vert et discussions résolues obligatoires.
Ces réglages ne remplacent ni la création contrôlée des futurs trains ni la preuve de leurs SHA.

## Définition de terminé

Le lot est prêt pour revue lorsque ses contrats shell passent dans une copie Git isolée, que le
diff est propre et que la Pull Request de bootstrap expose l'exception exacte. Sa fusion requiert
une revue humaine et un merge commit. Les premières branches `feature/V0.1.0` et
`release/V0.1.0` relèvent d'une opération distante séparée après cette fusion.

## Résultats d'exécution

Sur le diff final du 2026-09-05, avant publication de la branche de bootstrap :

- `sh ci/test-branch-name.sh` : succès, dont contexte `gitlab-branch` positif pour `main`, features
  d'intégration et releases exactes, et négatif pour Work Orders, bootstrap et branches historiques ;
- `sh ci/test-github-pull-request.sh` : succès, dont fixture Git réelle fondée sur la base
  historique exacte, tête descendante, tête divergente, version de bootstrap
  `0.1.0-SNAPSHOT` et mapping Maven stable/RC/RC-SNAPSHOT ;
- `sh ci/test-gitlab-workflow.sh` : succès, dont emploi explicite du contexte `gitlab-branch` pour
  les pipelines de branche push, web, schedule, API, trigger et pipeline, voies MR/tag séparées et
  refus d'une source sans ref déterminable ; les tags valides protégés passent, tandis que les tags
  non protégés ou mal formés sont refusés dans `validate:source` ; les quatre mélanges MR/branche,
  MR/tag, branche/variables MR et tag/variables MR sont également refusés ;
- `sh ci/test-gitlab-merge-request.sh` : succès, dont historique complet, source/main alignés,
  source ou pipeline décalé, cible divergente ou absente, historique shallow et release scellée ;
- `sh ci/test-release-reproducibility.sh` : succès, avec contrôle de la version d'une branche Work
  Order via `GITHUB_HEAD_REF` ;
- `sh ci/test-package-guards.sh` : succès avec code de sortie `0` dans une copie Git isolée, jusqu'à
  `RELEASE_REPRODUCIBILITY=PASS`, `PACKAGE_GIT_GUARDS=PASS` et
  `BP_FINAL_PACKAGE_GUARDS=PASS` ;
- `git diff --check` : succès ;
- copie Git temporaire de qualification supprimée après les tests.

Le scan exhaustif de secrets sera exécuté sur le commit candidat, afin que le script examine bien
les blobs Git du changement et non seulement le HEAD antérieur. Les suites Maven et PostgreSQL
restent à prouver sur ce même commit par les workflows Windows/Linux ; elles ne sont pas revendiquées
comme exécutées localement.
