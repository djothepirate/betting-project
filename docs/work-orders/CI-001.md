# CI-001 — Mettre en place la fabrique CI du Betting Project

- **Statut :** En cours — Pull Request en brouillon
- **Date d'ouverture :** 2026-09-01
- **Responsable de décision :** Porteur du Betting Project
- **Exécutant :** Codex
- **ADR applicables :** ADR-005, ADR-007, ADR-008
- **Branche de correction :** `codex/ci-20260902-002-maven-wrapper-extraction`
- **Amendement autorisé :** 2026-09-02 — mise en conformité du flux de promotion GitLab

## Objectif

Établir la gouvernance commune, le registre des dépôts officiels et une première fabrique CI capable
de vérifier le code et de produire des snapshots ou releases traçables, sans secret de production
et sans prétendre qu'un JAR isolé est déjà un bundle VPS.

## Périmètre autorisé

- enregistrer les décisions 1A, 2A et 3A dans ADR-008 ;
- enregistrer les deux dépôts officiels et leur classification ;
- étendre la CI GitHub existante avec des références conventionnelles et un artefact traçable ;
- ajouter une configuration GitLab CI Free pour Linux, Testcontainers, rapports et packaging ;
- produire JAR, SBOM CycloneDX, provenance et SHA-256 ;
- préparer des artefacts de snapshot et de tag sans les déployer ;
- documenter l'onboarding, le miroir, les protections et la rotation ;
- aligner la gouvernance et les garde-fous sur la promotion GitLab de `main` vers
  `release/<SemVer>` ;
- mesurer Javadoc, couverture et duplication sans inventer de baseline.

## Exclusions

- aucun secret, jeton, clé SSH ou variable sensible ;
- aucune activation du miroir dans ce lot ;
- aucun développement, push direct vers `release/*` ou commit propre à GitLab ;
- aucune modification du dépôt source du Local Lab dans cette Pull Request ; sa transposition passe
  par un lot sœur revu sur GitHub ;
- aucune création de branche de release pendant cette mise en conformité ;
- aucune fusion automatique ;
- aucun tag ou release créé ;
- aucun Dockerfile, accès SSH au VPS ou déploiement de production ;
- aucune baisse arbitraire d'un seuil qualité.

## Critères d'acceptation

- [x] ADR-008 formalise 1A, 2A et 3A.
- [x] Le registre contient les deux dépôts et distingue `vps-deployable` de `local-only`.
- [ ] La CI GitHub du merge synthétique courant de la Pull Request est verte sous Windows et Linux.
- [ ] Le premier pipeline GitLab est vert sur le même SHA.
- [ ] Les métriques qualité initiales sont mesurées puis verrouillées dans un commit distinct.
- [ ] Un snapshot contient le JAR, le SBOM, la provenance et les SHA-256.
- [ ] Deux générations successives du SBOM ont la même empreinte et aucun numéro de série.
- [ ] Le composant racine du SBOM est une application, référence ce dépôt et porte la licence
  provisoire `Proprietary` plutôt que les métadonnées héritées de Spring Boot.
- [ ] Un tag de release déclaré mais absent du checkout, hors de `main` ou incohérent avec la
  version Maven est refusé.
- [ ] Une version Maven finale non taguée reste un snapshot non promouvable et la PR de
  préparation peut être qualifiée avant la création du tag.
- [ ] Toute base de version Maven snapshot hors SemVer `X.Y.Z[-rc.N]` est refusée avant packaging.
- [ ] Aucun job GitLab de `main` ou de tag ne lit un cache Maven qu'une ref non protégée peut
  alimenter ; le cache partagé reste désactivé jusqu'à isolation serveur qualifiée.
- [ ] Une release taguée ne contient aucun identifiant de pipeline propre à une forge.
- [ ] GitLab est l'unique producteur du bundle tagué ; GitHub vérifie le tag sans le republier.
- [ ] Le projet GitLab du Local Lab existe et reste privé.
- [ ] La CI accepte uniquement `release/X.Y.Z` et `release/X.Y.Z-rc.N` parmi les branches de
  promotion et refuse leurs variantes SemVer mal formées.
- [ ] Une Merge Request GitLab est refusée si elle provient d'un fork, cible une branche non
  protégée, annonce une version Maven différente ou tente d'avancer une release déjà taguée.
- [x] Sur les deux projets GitLab, `main` est non protégée, `release/*` est fusionnable seulement
  par les Maintainers, le push direct et le force-push y sont interdits.
- [ ] La fusion GitLab est fast-forward sans squash et une release taguée pointe le même SHA que
  `main` canonique et sa branche `release/<SemVer>`.
- [ ] Les protections, la 2FA et le runner Testcontainers sont vérifiés avant activation du miroir.
- [ ] La revue humaine autorise explicitement la fusion.

## Commandes de test

```text
./scripts/check-no-secrets.sh --scope all --base <base>
./mvnw verify
./mvnw -Pintegration verify
sh ci/package-artifact.sh
git diff --check <base>...HEAD
```

## Séquence

1. Fusionner la gouvernance et la CI sans secrets.
2. Mesurer et verrouiller la baseline qualité ; ne pas fusionner le lot d'instrumentation seul.
3. Créer les projets GitLab, laisser `main` non protégée et protéger uniquement `release/*` contre
   tout push direct, avec fusion réservée aux Maintainers.
4. Synchroniser le SHA qualifié de `main`, puis vérifier un pipeline GitLab sur ce SHA exact.
5. Configurer les fusions GitLab en fast-forward sans squash et qualifier le chemin
   `main` vers `release/<SemVer>` avant la première release.
6. Préparer le miroir dans une Pull Request séparée, désactivée par défaut.
7. Qualifier le packaging VPS dans un Work Order séparé avant tout déploiement.

## Résultats d'exécution

### Qualification GitLab du 2026-09-02

- Le pipeline GitLab [#2](https://gitlab.com/djothepirate-betting-project/betting-project/-/pipelines/2811317529)
  atteint un runner partagé, puis le job `validate:source` échoue pendant `./mvnw -version`.
- Cause : en l'absence d'`unzip`, le wrapper remplace le ZIP déclaré par le tarball, puis compare
  celui-ci au SHA-256 du ZIP. Le checksum configuré du ZIP officiel reste correct et inchangé.
- La Pull Request GitHub [#6](https://github.com/djothepirate/betting-project/pull/6) conserve le ZIP
  vérifié, utilise l'outil JDK `jar` comme extracteur de repli et restaure le bit exécutable de
  `bin/mvn`. Elle reste en brouillon pour revue humaine.
- Le [run GitHub #54](https://github.com/djothepirate/betting-project/actions/runs/33575331749),
  déclenché pour le HEAD `096b54a565dadd5a242fbeced4a1501d79d1404b` et son merge synthétique
  `a16b8d4e85b52110fa3b51a76d35224e4678e05f` contre `main` au SHA
  `88194d9136611fe44a809d6e1acc91945b6639b9`, est vert sous Windows et Linux : tests standards,
  intégration PostgreSQL/Testcontainers, packaging et contrôle du diff réussissent.
- Cette preuve est historique : elle ne qualifie plus le HEAD fusionnable depuis que `main` a
  avancé au SHA `85dc943601a7d33d37ca69a0c913bf32f1162811`. La preuve finale est l'état des
  checks GitHub attachés au merge synthétique courant au moment de la revue ; aucun numéro de run
  antérieur n'est présenté comme une preuve du HEAD final.
- Validation locale ciblée : `bash -n ./mvnw`, cache Maven vierge, `unzip` et `python3` masqués,
  deux exécutions successives de `./mvnw -version`, Maven `3.9.16`, launcher exécutable et URL
  mémorisée identique au ZIP officiel. Résultat : `MAVEN_WRAPPER_JAR_FALLBACK=PASS`.
- Restent à qualifier après fusion humaine : synchronisation du nouveau SHA `main` vers GitLab,
  pipeline GitLab déclenché par `push`, jobs complets et artefact snapshot.

### Mise en conformité de la promotion du 2026-09-02

- La revue de la Pull Request `#6` a relevé que l'ancienne convention refusait `release/*`, que
  l'ADR interdisait encore les Merge Requests GitLab et que le runbook demandait de protéger
  `main`. Ces trois points contredisaient la décision opératoire du porteur.
- Le porteur a confirmé que `release` désigne le motif `release/*`, que les Pull Requests GitHub
  fusionnent les branches de travail vers `main` et que seule une Merge Request GitLab promeut
  ensuite `main` vers `release/<SemVer>`.
- La configuration cible conserve `main` non protégée, réserve la fusion de `release/*` aux
  Maintainers, interdit tout push direct et force-push, et exige un fast-forward sans squash afin de
  préserver le SHA canonique GitHub.
- Cette configuration est appliquée et relue sur les deux projets : fast-forward, squash interdit,
  rebase automatique désactivé, conservation de la source, pipeline réussi et discussions résolues
  obligatoires. La règle `release/*` reste l'unique protection de branche ; `main` reste non
  protégée.
- La validation locale de la mise en conformité est verte : convention des branches, matrice des
  Merge Requests GitLab, garde-fous Git/tag/release et reproductibilité du bundle ; 219 tests
  standards et 89 tests PostgreSQL/Testcontainers passent sans échec ; le contrôle de secrets est
  vert.
- Les garde-fous exécutables de cette Pull Request portent uniquement sur `betting-project`. Le
  réglage serveur fast-forward est commun aux deux projets, mais la CI actuelle de
  `betting-sofascore-local-lab` refuse encore le pipeline de push d'une branche `release/*` et ne
  contrôle pas l'identité tag/branche. Toute promotion ou tout tag GitLab du Local Lab reste donc
  interdit jusqu'à une Pull Request sœur appliquant les mêmes invariants.
- Le bootstrap de la première branche de release est documenté comme une création GitLab via
  interface ou API, sans push : protection temporaire exacte de `main`, création sur un ancêtre du
  candidat, puis retrait immédiat de cette protection. Les branches suivantes partent de la
  précédente branche de release protégée.
- La branche de correction intègre le `main` courant `85dc943601a7d33d37ca69a0c913bf32f1162811`
  par le commit de fusion `bc5b545`. Elle doit encore obtenir de nouveaux checks Windows et Linux
  verts sur son merge synthétique après publication avant toute approbation.

## Définition de terminé

La Pull Request reste en brouillon tant que les pipelines réels et la baseline ne sont pas
qualifiés. La fusion relève exclusivement de la revue humaine prévue par ADR-005.
